# MCP capabilities for an external-document GraphRAG workflow

Checked: 2026-10-16. Scope: capability fit and a bounded next experiment; no implementation or model execution. External sources below are official MCP specifications only.

## Finding

The existing tools already provide the main agent connection. The immediate goal is connect-once onboarding: after connection, the agent should discover the workflow, extraction schema, recovery rules, and evidence through MCP without reading this repository. Improve these contracts and evidence access before introducing server-owned orchestration. Resources can expose instructions and evidence on demand, and prompts can package extraction instructions. Neither feature needs a new database or service. These are recommendations, not implemented behavior.

## Observed repository state

- [Server](../../src/preciso_mcp/server.py): Python SDK `mcp.server.fastmcp.FastMCP`, 11 tool registrations, default `mcp.run()` transport; no resource or prompt registrations, explicit tool annotations, sampling, elicitation, task handling, or application progress reporting.
- Tool functions return broad `dict` values. Application failures can be returned as `status: error` or `validation_failed`; this alone does not explicitly set MCP `isError`. SDK-generated schemas and envelopes must be inspected on the wire before concluding that structured output is absent.
- `query_graph_tool` returns evidence through `raw_data`, including chunks and references. Its documented source references include `file_path`, `source_id`, and `chunk_id`. An empty result has a different object shape from a populated result.
- [Operation guide](../mcp-server.md): agents extract and review original documents externally; ingestion is additive, identical replay is for recovery, and correction requires a complete fresh rebuild. One runtime owns each graph directory. Local graph/vector/KV artifacts remain the retrieval backend; Neo4j and Qdrant tools are exports. Ollama is the default embedding provider; cloud embedding configuration does not itself provide document extraction.
- Read-only inspection of the installed environment found **mcp 1.27.2** in `.venv/lib/python3.13/site-packages/mcp-1.27.2.dist-info/METADATA`. `mcp/types.py` defines `LATEST_PROTOCOL_VERSION = "2025-11-25"`; `mcp/shared/version.py` lists `2024-11-05`, `2025-03-26`, `2025-06-18`, and that latest value. This is local environment evidence, not proof of another machine's installed SDK or a client's capabilities.

## Version boundary

The official [versioning page](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning) identifies **2026-07-28** as current, ready for use. It distinguishes current, final, and draft revisions. Therefore 2025-11-25 must not be described as the latest specification.

The official [2026-07-28 changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog) remove the initialization handshake, add per-request version/capability metadata and `server/discover`, and replace server-initiated input requests with an `InputRequiredResult` retry flow. Sampling and roots are deprecated; experimental tasks move from core to a redesigned official extension. These are specification changes, not capabilities supplied by this installed SDK.

Use the mutually supported protocol and actual client capabilities. The capability descriptions below use **2025-11-25**, which matches the inspected SDK's newest supported version. Do not mix its handshake/task messages with 2026-07-28 messages or force all clients to use the newest revision. Client interoperability remains untested.

## Capability fit

| Capability | Protocol fact | Fit and limitation |
|---|---|---|
| Tools | `structuredContent` carries result data; `outputSchema` constrains it. When provided, results must conform; clients should validate. Serialized JSON text is recommended for compatibility. Tool execution failures use `isError: true`; malformed RPC requests are separate protocol errors. [Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) | Give ingestion and retrieval stable machine-readable outcomes. MCP output schemas do not make an agent's extraction factually correct. |
| Tool annotations | `readOnlyHint`, `destructiveHint`, `idempotentHint`, and `openWorldHint` describe behavior; all are hints. [Schema](https://modelcontextprotocol.io/specification/2025-11-25/schema#toolannotations) | Help clients present status/query versus mutation/export operations. Hints neither authorize calls nor enforce permissions. Consider provider network effects before marking `openWorldHint: false`. |
| Resources and links | Resources are URI-addressed context, read through `resources/read`; templates parameterize access. Host applications decide how context is used. Tool results can include resource links that need not appear in `resources/list`. [Resources](https://modelcontextprotocol.io/specification/2025-11-25/server/resources), [links](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#resource-links) | Expose bounded source chunks and document manifests through stable opaque URIs. A link is not automatic context inclusion, file download, or authorization. Retain inline evidence/tool fallback for clients that do not fetch resources. |
| Prompts | Discoverable, argument-driven message templates are intended for explicit user selection. [Prompts](https://modelcontextprotocol.io/specification/2025-11-25/server/prompts) | Package extraction and cited-answer instructions. A prompt does not run the model, schedule work, validate evidence, or ensure clients select it. |
| Roots | Supporting clients expose relevant filesystem locations. Current roots are explicitly informational and deprecated; new implementations should use parameters, resource URIs, or configuration. [Current roots](https://modelcontextprotocol.io/specification/2026-07-28/client/roots) | Keep configured input directories and server-side path validation. Roots do not enforce filesystem security or grant access to remote client files. |
| Sampling | A supporting client can provide model generation; client controls model access and may decline. Tool-enabled sampling requires `sampling.tools`. [2025 sampling](https://modelcontextprotocol.io/specification/2025-11-25/client/sampling) | Could request extraction or summary generation without server API keys on compatible clients. It cannot be assumed on arbitrary clients and is now deprecated. Keep external-agent extraction as the baseline. |
| Elicitation | Client-mediated forms or URLs request user information; modes require client support. Form mode must not collect secrets. [Elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation) | Optional clarification of document identity or intent. It is not a substitute for server authorization or evidence review, and unattended clients may have no interactive UI. |
| Progress and cancellation | Progress is optional and uses a request's `progressToken`; notifications must increase and stop at completion. Cancellation requests termination, but may arrive too late or be ignored when work cannot be cancelled. [Progress](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/progress), [cancellation](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation) | Report embedding/validation/commit stages and document safe cancellation boundaries. Cancellation does not imply rollback of committed graph changes. |
| Tasks | The 2025 feature is experimental, with polling, deferred results, explicit capabilities, and per-tool `execution.taskSupport`. [Tasks](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks) | Potential fit only for demonstrated long-running batch work. Do not promise durable jobs across process restart or arbitrary client support. The current extension differs; its adoption needs a separate compatibility decision. |

## Recommended order

1. **Make one supported client seamless first.** Test its negotiated version, capabilities, tool schemas, and envelopes. Put concise workflow guidance in server/tool descriptions and expose the extraction schema and recovery rules through MCP-readable context, with a tool fallback where needed. The agent should not need repository paths to learn how to use the server. Keep the existing runtime and storage.
2. **Define typed results and errors.** Use consistent status, counts, validation details, provenance, and empty-result fields. Map application failures to MCP execution errors with actionable feedback. Verify SDK behavior rather than assuming `dict` annotations produce useful schemas. [Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)
3. **Add honest annotations.** Mark status and pending-work reads appropriately; distinguish ingestion, summary writes, and exports. Exports with `clear_existing` need conservative destructive metadata. Claim idempotence only after verifying all effects. [Annotation meanings](https://modelcontextprotocol.io/specification/2025-11-25/schema#toolannotations)
4. **Make evidence addressable across boundaries.** Prototype bounded chunk resources and document manifests with version/hash metadata and links beside compact query evidence. Use opaque server URIs. Keep inline tool evidence as fallback. A host path is not automatically visible inside a container: retain inline extraction ingestion, or document an explicit input mount. Original document upload/reading is a separate proposed capability; resources alone do not transfer client files to this server. [Resources](https://modelcontextprotocol.io/specification/2025-11-25/server/resources)
5. **Package the external-agent workflow.** Offer extraction and cited-answer prompts with stable source/chunk IDs, validation instructions, and reviewed ingestion steps; retain equivalent documentation for hosts without prompt discovery. [Prompts](https://modelcontextprotocol.io/specification/2025-11-25/server/prompts)
6. **Improve long-operation feedback before jobs.** Add stage progress and test cancellation around transaction boundaries. Retain bounded synchronous calls until actual duration/client timeout evidence justifies task machinery. [Progress](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/progress), [cancellation](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation)
7. **Keep optional orchestration optional.** Do not build new dependencies on deprecated roots/sampling. Gate elicitation by supported mode. Assess the tasks extension only after confirming a specific target SDK/client pair and a batch-processing need. [Current changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

## First experiment: existing stdio client

Proposed, **not executed**: use an already installed client with a temporary empty graph directory and the existing provider configuration. Record its initialization response and `tools/list`. Call `get_server_status`; stop if embeddings are degraded. Have the agent extract a tiny known document such as “Mira owns the archive service,” review it, call `ingest_graph_tool`, then `query_graph_tool` with “Who owns the archive service?” Ask the agent to cite the returned original chunk. Finally submit one structurally invalid extraction and inspect both application status and MCP `isError`.

Success: the agent discovers and executes the workflow without manual tool-name coaching or repository access, handles validation failure as failure, and grounds its answer in the original chunk and stable source identity. Record any missing schema/instructions, envelope visibility, token size, latency, and host capability gaps. Repeat the same inline payload across a container boundary if that is the deployment target; test mounted file input separately. This tests the existing connection and identifies the smallest next contract change; it does not establish retrieval quality at corpus scale. Do not use the production graph for this experiment. No new service, task runtime, or sampling support is required.
